# PR85：驱动升级失败的根因与修复

适用范围：virtio-win-guest-tools-installer 的驱动安装 CA（`src/DrvInst/DrvInstCA`）与 WiX 调度。
状态：研究分支，未签名，未提交上游。不宣称通用修复。

## 1. 问题

升级 virtio-win（例如 0.1.248 → 0.1.285）时 MSI 返回 1603，驱动处于半装状态。
原 PR85（`b7be410`）的做法：

- `UninstallDriverPackages` 改为 `Return='ignore'`
- `MajorUpgrade` 改为 `afterInstallExecute`
- 卸载时加 `DIURFLAG_NO_REMOVE_INF`，把旧包留给系统

这三项让失败"看不见"，没有消除失败原因：错误被忽略后，系统可能留下无驱动的设备、指向已删除文件的服务、无人拥有的驱动包。

## 2. 排查结论：到底是什么错了

所有失败都不是"旧驱动释放不了资源"。设备无法热切换时，Windows 本来就会标记重启（3010），重启后新驱动接管，这条路径在测试中一直正常。真正的失败点如下（均在 VM 上复现）：

| # | 现象 | 根因 | 类别 |
|---|---|---|---|
| R1 | 官方升级在"历史受损"的机器上 1603，`DIFXAPP ERROR 0x2 … persistent-info key` | DIFx 依赖自己的持久化注册表记录；记录缺失时，它在操作任何设备之前就拒绝 | 所有权元数据损坏 |
| R2 | 官方在策略阻止安装、或部分升级时返回 0，但设备没有驱动 | 卸载/安装错误被吞掉（`ignore`、DIFx 内部忽略） | 错误被忽略 |
| R3 | 卸载旧产品 = 删除驱动包；major upgrade 先删后装或先装后删，任一步失败都不能整体撤回 | 驱动操作不在 MSI 事务里：没有回滚脚本对应真实的系统操作 | 缺少事务 |
| R4 | viostor 返回 `ERROR_NO_MORE_ITEMS` 被当成致命错误 | 这个返回值的意思是"包已入库，没有设备需要更新"，属于成功 | 返回值误读 |
| R5 | 回滚时删除新包失败 `0xe000023d` | 父设备绑定新驱动后，复活了一个隐藏的 VIOINPUT 子设备，子设备占用新包；Windows 对"删除仍被引用的包"直接拒绝，不会推迟到重启 | 回滚依赖顺序 |
| R6 | 回滚后服务 `ImagePath` 指向已删除的包 | 新包安装时改写了已存在服务的配置，回滚没有还原 | 回滚不完整 |
| R7 | x86 受损历史上 `0x80070002` | 一个不在场的子设备仍引用已删除的包（`oem8.---`） | 悬空引用 |
| R8 | x86 + 0.1.285 驱动：`0x800b0109` | 上游 285 x86 驱动只有自签名 "Red Hat Inc."，系统不信任 | 上游签名，非安装程序问题 |

## 3. 修复思路

原则：用平台自己的所有权和事务语义，每一步正向操作都有一个可校验的逆操作；不靠忽略错误，不备份整个注册表，不伪造所有权。

1. **原生驱动事务**（`DriverTransaction.cpp/.h`，取代 DIFx 路径）
   - 正向：`SetupCopyOEMInf`（NOOVERWRITE，记录是否本次新建）→ 一次 `DiInstallDriverW(flags=0)`，由 Windows 选择设备，不强制。
   - 写前日志：每个操作之前把意图和捕获的旧状态写进 WiX 回滚脚本（每组独立 GUID）。
   - 逆操作：按逆序比较当前绑定与捕获绑定，只还原变了的；用精确的旧包/节或 NULL 驱动；只删除本次新建的包，且在绑定还原之后，不强制。
   - 不删除设备节点，不调用 `DiRollbackDriver`，不做全局重扫。
2. **所有权元数据**：每个组件一条 GUID 键，记录包身份（INF/CAT 的 SHA256）和"是否由本组件创建"。来源不明的包一律视为非本组件所有，只删除自己的元数据（R1、R2）。
3. **调度**：安装在 `InstallFiles` 之后，卸载在 `RemoveFiles` 之前；`MajorUpgrade` 放在 `InstallExecute` 之后，旧产品的卸载与新产品的安装在同一事务里；要求回滚开启（`NOT RollbackDisabled`）。所有驱动 CA 都是 `Return='check'`（R3）。
4. **准入**：`CheckLegacyDriverOwnership` 在 `InstallInitialize` 之前只读检查，如果 major upgrade 会移除某个旧驱动的最后一个所有者，就直接拒绝并提示先保留驱动升级、再用维护模式改功能。这是设计边界，不是部分升级成功。
5. **逐个修复观察到的失败**：
   - R4：`ERROR_NO_MORE_ITEMS` 在核对入库身份和绑定后视为"仅入库成功"。
   - R5：范围包含在场父设备的不在场直接子设备，先捕获父再捕获子，逆操作先子后父；两遍构建，不依赖枚举顺序，发现环就拒绝。
   - R6：对 INF `AddService` 指向的已存在服务，用 SCM 捕获 ImagePath/类型/启动/错误控制/LoadOrderGroup，回滚时先复核再 compare-and-set 还原。
   - R7：只有"设备不在场 + 包名无法解析到存储路径"时，才把绑定当作 NULL 驱动。读取一个存在的包出任何错，仍然失败退出（独立评审后收窄，见时间线 N35）。
6. **形式化**：`docs/programming-thinking/driver-upgrade-reliability.idea.lean` 用有限模型记录不变式（条件性事实，不是对 Windows 的证明）。

## 5. 验证（N35）

- 主机：4 个 C++ 单元测试、`test/test_native_contracts.py`、Lean 模型。
- x64 Windows 11 LTSC 2024（26100.1742）与 x86 Windows 10 22H2（19045.2965），官方 248 历史 + 受损变体：
  - 升级 → 再升级 → 卸载：全部 0，服务运行。
  - 故障注入（前/后）、真实错误（DenyDeviceIDs）、安装末尾取消：1603/1602，重启后捕获的语义字段与之前一致。
  - 受损历史修复：x64、x86 均通过（官方安装包在同样的机器上失败）。
  - 维护模式移除/加回 balloon：通过。
- 对照：官方安装包在同样场景下要么 1603（R1），要么返回 0 但留下无驱动设备（R2）。

## 6. 已知边界与未决

- 只测了两个系统版本、一种安装历史。
- 不还原：经由不匹配中间节点的后代设备、新出现/消失的设备节点、新建服务、通过 Include/Needs 引用的服务、并发外部修改。
- 回滚后被复活的悬空子设备会是 NULL 驱动，而不是原来那个悬空的包名。
- 未查明：`Error in rollback skipped. Return: 5`；设备属性 `{83da6326…}[4]` 残留；上游 NIC 配置 CA 留下的空 `viocfg.cfg`。
- x86 发布 285 驱动需要上游重新签名。
- 仓库里的 `Libraries/` 二进制是旧的上游产物，本分支没有替换；测试使用的 CA 由源码构建。
